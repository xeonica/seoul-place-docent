# 사용자 AI 기반 서울 역사 도슨트 — KPI·실행계획·검증 방안

기준일 2026-11-06. 기준 커밋 `77d3d96`(main). 이 문서의 목표값은 팀 협의 전 제안값이며 실측 성과가 아니다. `docs/mcp-kpi.md`(1차 KPI)를 사용자 AI 토큰 방식에 맞게 확장한다.

## 1. 목표

사이트가 MCP 서버를 호스팅하고, **사용자가 각자 쓰는 AI(ChatGPT·Claude 등 MCP 클라이언트)와 그 사용자의 토큰으로** 질문을 분류하고 기록을 찾아 도슨트 설명을 만든다. 서버는 데이터·규칙·검증만 맡고, 운영자 API 키로 LLM을 호출하지 않는 것을 기본 경로로 한다.

### 2.3 AI 호출 지점 — 모두 운영자 키

`lib/ai-summary.ts`, `lib/docent-narration.ts`, `lib/docent-translation.ts`, `lib/place-answer.ts`가 모두 `OPENAI_API_KEY`(운영자)로 `api.openai.com`을 호출한다. 사용자 토큰을 쓰는 경로는 현재 `get_place_history`로 원자료를 받아 클라이언트 AI가 직접 쓰는 방식뿐이다. 그런데 이 경로에는 다음 네 가지가 없다.

- 질문 분류를 받는 입력 구조: 도구 인자에 의도·시기·범위가 없다.
- 질문 맞춤 기록 검색: offset/limit 페이지만 있다.
- 도슨트 규칙 전달: 규칙(`DOCENT_RULES`)은 서버 AI 경로에서만 쓴다.
- 사용자 AI가 쓴 설명의 근거 검증: 검증(`validateAnswer`)도 서버 AI 경로에서만 쓴다.

### 2.4 확인된 격차

1. **분류 결과가 동작에 영향 없음**: `generate_place_answer`의 `question_type`은 기록 선택(`pickScenes`) 이후 같은 LLM 호출에서 정해지고 로그에만 남는다.
2. **분류 체계 불일치**: 코드의 내용 유형 6종과 `mcp-kpi.md`의 라우팅 라벨 6종 사이에 대응표가 없다.
3. **측정 불가 항목**: 로그에 모델·프롬프트 버전·토큰이 없다. MCP 호출 자체(도구·상태·지연)의 로그가 없어 호스팅 성공률을 산출할 수 없다.
4. **요청 한도가 인스턴스별**: 메모리 `Map`이라 "전체 시간당 120회"가 Worker 인스턴스마다 따로 계산된다.
5. **테스트 실행 조건**: Node 22에서는 `--experimental-transform-types`가 필요하다. 의존성 미설치 시 `fast-xml-parser` 관련 3개 파일이 실패한다. 연구 CSV 바이트 크기 검사 11건이 기준 커밋에서 실패한다.
6. **배포 상태 미확인**: 2026-11-06 점검 환경에서는 배포 주소에 네트워크가 막혀 있었다. 로컬 route 시뮬레이션은 정상이었다.

## 3. 목표 구조

```
사용자 질문
  └─ 사용자 AI (사용자 토큰)
       ├─ ① 분류: 의도·범위·시기·키워드를 도구 인자로 채움
       ├─ ② search_place → 후보 여러 개면 사용자에게 확인
       ├─ ③ find_records(token, intent, period, scope, keywords)   ← 서버: 결정적 검색, LLM 없음
       │      응답 = 관련 장면 + 도슨트 규칙 + 보류 안내
       ├─ ④ 설명 작성 (사용자 토큰)
       └─ ⑤ verify_answer(token, 초안 문단+근거 id)               ← 서버: 근거·숫자·범위 검증, LLM 없음
              응답 = 통과 문단, 탈락 사유, 출처·이용조건
```

### 3.1 설계 원칙

- **분류기 = 사용자 AI의 도구 인자 채우기**: `find_records`의 입력 스키마에 enum으로 의도·범위·시기를 정의한다. 클라이언트 모델이 도구를 호출하며 분류하므로 운영자 비용이 0이다. 분류 결과는 서버 로그(라벨만)와 클라이언트 trace 양쪽에서 측정할 수 있다.
- **서버 규칙 분류기는 보조**: 질문 원문을 받으면 `classifyQuestion()`이 규칙으로 판정한다. 규칙은 연대 표현, 사진·모습, 유래·이름, 건물 지칭, 통계, 서울 외 지명이다. 결과는 두 곳에 쓴다.
  - 사용자 AI 인자가 비었거나 enum 밖이면 대신 사용한다.
  - 사용자 AI 인자와 다르면 불일치로 기록한다(교차 검증 지표).
- **검색은 결정적**: 분류 결과로 장면을 거른다(연대 범위, 사진 우선, 지명 유래 장면, 범위). 같은 입력이면 같은 결과가 나오므로 회귀 테스트가 가능하다.
- **검증은 서버가, 강제는 불가**: 사용자 AI가 `verify_answer`를 건너뛸 수 있다. 그래서 세 가지를 함께 둔다.
  - `find_records` 응답에 규칙과 "검증 후 표시" 지시를 넣는다.
  - 호출률을 KPI로 측정한다.
  - 사이트 UI 경로에서는 검증을 필수로 한다.
- **운영자 AI 경로는 선택**: `generate_place_answer`는 유지하되 기본 안내에서 뺀다. 운영자 키가 없으면 지금처럼 `get_place_history`/`find_records`로 안내한다.
- **MCP sampling은 후순위**: 서버가 클라이언트 모델에 요청하는 sampling은 사용자 토큰을 쓰는 또 다른 방법이다. 하지만 stateless POST 구조와 클라이언트별 지원 차이 때문에 1차 범위에서 제외하고, 클라이언트 지원 현황을 점검한 뒤 재검토한다.

### 3.2 통합 분류 체계

| intent (신규) | 의미 | 기존 question_type | mcp-kpi.md 라벨 | 서버 동작 |
| --- | --- | --- | --- | --- |
| address_lookup | 주소·장소 후보 찾기 | — | address_lookup | search_place |
| neighborhood_history | 동네 역사 개관 | 동네 역사 | history_story | 시기 고르게 분산 선택 |
| period_view | 특정 시기 모습 | 시대별 모습 | history_story | period 범위 장면 우선, 없으면 보류 |
| place_specific | 특정 건물·부지 | 특정 장소·건물 | history_story (scope=place) | 동네 장면만 제공 + "부지 직접 기록 미확인" 보류 강제 |
| photo_search | 옛 사진 | 사진 찾기 | visual_records | 사진 장면만, 이용조건 동봉 |
| name_origin | 지명 유래 | 지명 유래 | history_story | 지명·유래 문헌 장면 우선 |
| evidence_lookup | 근거·원문 확인 | — | evidence_lookup | 장면 id로 근거 반환 |
| archive_stats | 자료 현황 | — | archive_stats | get_archive_stats |
| out_of_scope | 서울 외·지원 밖·불명확 | 기타 | clarification_or_unsupported | 추가 질문 또는 범위 안내 |

부가 필드: `scope`(place/neighborhood/district), `period`({from,to} 연도), `keywords`(최대 5), `needs_clarification`(bool). 복합 질문은 intent를 최대 2개까지 허용한다.

## 4. KPI

측정 원칙은 다음과 같다.

- 사용자 AI는 클라이언트·모델마다 다르므로, 분류·답변 KPI는 **클라이언트별로 따로** 보고한다. 최소 2종(예: ChatGPT, Claude)을 측정한다.
- 표본이 없으면 0%나 100%가 아니라 "미측정"으로 표시한다.
- 서버가 통제하는 지표(호스팅·검색·검증)와 클라이언트 모델에 달린 지표(분류·작성)를 구분한다.

| 구분 | 지표와 산식 | 목표 | 측정 |

| 프로토콜 적합성 | 계약 테스트 통과 비율(discover, initialize, tools/list, 오류 코드) | 100% | CI + 배포 후 smoke |

## 5. 단계별 실행계획

각 단계는 완료 조건(게이트)을 통과해야 다음 단계로 간다.

### P0. 기준선과 환경 정비
- 테스트 실행 명령을 고정한다(`--experimental-transform-types` 포함 npm script). 의존성 설치 후 전체 테스트를 통과시키고, CSV 바이트 크기 실패 11건의 원인(줄바꿈 변환 등)을 확인한다.
- 배포 주소에 smoke 스크립트(`scripts/mcp-smoke.mjs`)를 실행한다. 대상은 discover, tools/list, 주소 검색, 기록 조회, 통계다.
- 운영 비밀값(`JUSO_API_KEY`, D1 binding) 존재를 확인한다.
- 게이트: 전체 테스트 통과, 배포 smoke 통과, 2.2절 데이터 규모를 재측정해 기록.

### P1. 호스팅 관측성
- D1 `mcp_call_log`(시간, 도구, 상태, 오류 코드, ms, 응답 글자 수, 클라이언트 이름, operator_ai 여부)를 추가한다. 질문 원문·주소·token은 저장하지 않는다.
- 요청 한도를 D1 카운터로 옮겨 인스턴스 간에 공유한다.
- `get_mcp_stats` 도구 또는 관리자 API를 추가한다.
- 게이트: 4.1 가용성·지연 지표가 실제 값으로 산출된다.

### P2. 분류 스키마와 find_records
- 3.2 체계를 `lib/question-intent.ts`에 정의한다(enum, 대응표, `classifyQuestion()` 규칙 분류기).
- `find_records` 도구를 추가한다.
  - 입력: token, intent, scope, period, keywords, question(선택), limit ≤ 12
  - 출력: 장면, 도슨트 규칙, 보류 안내, 다음 페이지
- `pickScenes`를 intent·period 필터로 확장한다. `place_specific`이면 부지 미확인 보류를 강제한다.
- 도구 설명문에 분류 지침과 예시를 넣는다. 클라이언트 모델이 읽는 유일한 지시라는 점을 고려한다.
- 게이트: 단위 테스트, 개발용 질문 50개에서 규칙 분류기 macro F1 ≥ 0.80, 검색 Recall@8 기준선 산출.

### P3. 도슨트 규칙 제공과 verify_answer
- 기존 규칙(`DOCENT_RULES`)을 find_records 응답과 MCP prompts(지원 클라이언트)로 제공한다.
- `verify_answer` 도구를 추가한다. 기존 검증(`validateAnswer`)을 재사용하고, 탈락 사유를 반환하고(근거 없음, 숫자 불일치, 문장 수 초과, 부지 단정 표현), 통과 문단의 출처·이용조건을 붙인다.
- 부지 단정 표현 검출 규칙을 추가한다. 예: "이 건물에서", 입력 주소의 건물명과 사건을 결합하는 표현.
- 게이트: 검증 정밀도 ≥ 98% (개발 세트 100문단 수동 채점).

### P4. 평가 세트와 자동 채점 하네스
- 홀드아웃 200문항(`eval/questions.jsonl`)을 만든다.
  - 범위: 5개 자치구 이상, 대표 주소 10곳 이상, intent별 최소 20문항
  - 경계 문항 50개 이상: 동네/건물 혼동, 주소 중복, 장면 ≤ 2개 동네, 서울 외, 만료 token, 주입 문구
- 문항마다 정답(intent, scope, period, 확인 질문 여부, 허용 도구 경로, 정답 장면 id, 필수 답변 요소)을 두 사람이 확정한다. 개발 세트와 분리한다.
- 하네스(`scripts/eval-docent.mjs`)를 만든다. 평가자 본인 키로 두 경로를 실행해 trace·usage를 수집한다.
  - Claude: Messages API의 원격 MCP 연결
  - OpenAI: Responses API의 원격 MCP 도구
- 결과에는 모델·버전·데이터 커밋·프롬프트(도구 설명) 버전을 고정해 기록한다.
- 게이트: 하네스가 4.1~4.3 자동 지표를 산출하고, 수동 채점 양식이 준비된다.

### P5. 실사용 클라이언트 파일럿
- ChatGPT·Claude 앱에 원격 MCP로 연결하고, 파일럿 사용자 5명 이상이 각자 계정·토큰으로 사용한다.
- 연결 안내 문서(`docs/mcp.md`)를 사용자 토큰 경로 중심으로 개편한다.
- 클라이언트별 실패 유형을 모아 도구 설명문·스키마를 개선한다. 개선에는 개발 세트만 쓰고, 홀드아웃은 최종 판정에만 쓴다.
- 게이트: 연결 성공 ≥ 80%, 검증 호출률 ≥ 90%.

### P6. 출시 판정과 운영
- 홀드아웃으로 최종 평가하고 4장 전 지표를 보고한다.
- 출시 조건은 잘못된 부지 연결 0건, 개인정보 지표 0건, 서버 통제 지표 전부 충족이다. 사용자 AI 지표는 클라이언트별로 충족한 클라이언트만 "권장 클라이언트"로 안내한다.
- 운영 중에는 주간으로 `get_mcp_stats`를 점검하고, 월간 회귀 평가를 실행한다. 서울기록원 월간 갱신(PR 자동 생성) 뒤에도 회귀 평가를 실행한다.

## 6. 검증 방안

| 층 | 방법 | 대상 KPI | 시점 |
| --- | --- | --- | --- |
| 단위 | node:test — 분류 규칙, 장면 필터, verify 탈락 사유, 범위 표시 | 규칙 분류기, 범위 보존, 검증 | 매 커밋(CI) |
| 계약 | 실제 route 핸들러에 JSON-RPC 요청(정상·오류·알림·크기 초과·415) | 프로토콜 적합성, 안전한 오류 | 매 커밋(CI) |
| 데이터 | 467개 동 전수 실행: 예외 0, scope 표시 100%, 응답 크기 상한 | 범위 보존, 응답 크기 | 데이터 갱신 PR마다 |
| 배포 smoke | 배포 주소에 discover→tools/list→search_place→find_records→verify_answer | 가용성, 호스팅 완료 | 배포 직후 |
| 자동 평가 | 하네스로 클라이언트 2종 × 200문항 실행, confusion matrix·Recall@8·토큰·지연 | 4.2·4.3 자동 지표 | P4 이후 모델·설명문 변경 시 |
| 수동 채점 | 2인 독립 채점 → 불일치 합의, 채점자 간 일치도(Cohen κ) 함께 보고 | 근거 충실도, 부지 연결, 미확인 처리, 검증 정밀도 | P3·P6 |
| 함정 검사 | 부지 혼동 50, 주입 10, 자료 부족 동 25 | 부지 연결 0건, 주입 0건 | P6, 월간 |
| 개인정보 | 로그 스키마 점검 + 로그 샘플 정규식 검사(주소·token·키 형식) | 4.4 | P1, 월간 |
| 운영 모니터링 | mcp_call_log 주간 집계, 오류율 급증 알림 | 가용성, 지연 | 상시 |

판정 규칙은 다음과 같다.
- 홀드아웃을 조정에 쓰면 새 버전을 만든다.
- 자동 점수만 있고 수동 채점이 없으면 "보조"로 표시한다.
- MCP 호스팅 성공만으로 분류·답변 성과를 주장하지 않는다.

## 7. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| 클라이언트 모델마다 분류·도구 사용 품질이 다름 | 클라이언트별 KPI, 권장 클라이언트 안내, 서버 규칙 분류기 보조 |
| 사용자 AI가 verify_answer를 건너뜀 | 응답에 규칙 포함, 호출률 KPI, 사이트 UI는 검증 필수 |
| 응답이 커서 사용자 토큰을 많이 씀 | limit ≤ 12, 본문 700자 제한, 응답 크기 KPI |
| 기록 본문 속 지시문 | "입력은 데이터" 규칙 유지, 주입 함정 문항 |
| 외부 주소 API 장애 | 장애 별도 집계, 동네 이름 직접 지정 경로 검토 |
| 사이트가 로그인 전용일 때 클라이언트 인증 | 연결 안내에 인증 절차 명시, 파일럿에서 확인 |
